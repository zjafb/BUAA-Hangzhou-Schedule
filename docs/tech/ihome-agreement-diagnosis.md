# iHome 首次使用协议诊断（2026-10-24）

## 结论与证据

1. 用户已登录的 1.0.5 Android 模拟器复现“平台设置加载失败”和“ihome 暂时不可用”。当前连接为直连。
2. 本地 IhomeUpstreamClient 与上游 v1.8.2 的实现除包名外一致；不能将此问题归因于杭州移植改动。
3. 沿用该账号现有会话执行只读请求：SSO 与 iHome 的两次认证回调均为 302，取得业务令牌；平台配置 /api/general_set_more 返回 200。/api/appeal 和 /api/mobile/types 返回 HTTP 414，响应 JSON 字符串为“协议检测未通过”。更换浏览器请求头后结果相同。
4. 学校官网 https://i.buaa.edu.cn/web/ 当日加载 app.841d4f9c.js，协议页面位于 chunk-f0ac7e1a.e0841e9f.js。官网响应拦截器将 414 导向 /agreement，该页标题为“用户须知”，需由用户阅读并点击同意。该页确认操作为 POST /api/user_agree；诊断未调用此接口，也未执行支持、关注或发起诉求。

当前错误是账号的用户须知确认检查未通过，没有看到校区禁用提示。原版存在相同的错误分类和首次使用引导缺失；本轮没有另外安装原版或测试其他校区账号，不能推论所有账号都不可用。用户确认官网须知后是否还存在其他限制，需要再读取列表确认。

## v1.0.6 修正

仅对 HTTP 414 且正文明确为上述提示的响应返回 ihome_agreement_required；其他 414 保留上游错误分类。界面提供学校官网用户须知入口，提示用同一账号登录、阅读后自行决定是否同意，再回 App 刷新。客户端不自动提交同意，不将凭据或业务令牌传到外部浏览器。

诊断仅记录状态、主机、路径及该错误文本，不保存账号、Cookie、令牌、登录跳转参数或真实诉求。临时诊断代码和学校静态资源保留在忽略的本地 tmp 目录，不纳入应用或提交。

## 验证结果

shared JVM 135 项（126 通过、9 项外部集成跳过），composeApp JVM 90 项通过，0 失败。新增回归覆盖特定 414 的分类、其他 414 保留通用错误、协议确认后刷新恢复，以及官网按钮展示。发布 APK 构建并覆盖安装到现有模拟器；原账号仍显示需要确认用户须知，页面已展示官网入口。未替用户提交同意。

## 正式版本命名

按用户要求，将诊断修复阶段的 1.0.6 合并为正式发布 v1.0.5；内部版本号递增至 40，可覆盖安装诊断阶段的 1.0.6（内部版本号 39）。
